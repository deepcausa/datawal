# v0.1.0-alpha reference bench run

A single reference run, frozen at the v0.1.0-alpha tag. **This is not
a specification. It is not a target. It is not a guarantee.** Your
numbers will differ -- often substantially -- depending on filesystem,
storage class, CPU, kernel, and what else is running on the box.

The point of this document is to give you something to compare against
if your local numbers look wildly off (10× worse: probably bug or slow
disk; 10× better: implausible, check your fsync semantics).

For methodology, what each bench measures, and how to read Criterion
output, see [`../benchmarks.md`](../benchmarks.md).

## Stack

| | |
| --- | --- |
| Date | 2026-05-20 |
| OS family | Linux |
| Filesystem | ZFS, raid1 mirror, default tuning, no SLOG |
| Storage class | NVMe with power-loss-protection (PLP) |
| Architecture | x86_64 |
| Rust toolchain | stable, release profile, default codegen |
| Criterion | 0.5.x, default sampling (100 samples, 5 s measurement) |

A note on the storage class: NVMe drives with PLP can legitimately
acknowledge `fsync` in single-digit microseconds because the controller
considers writes durable once they reach the supercapacitor-backed
write cache. The observed fsync latencies below reflect that. On
consumer SSDs without PLP, expect fsync latencies one to two orders of
magnitude higher.

## `record_log` -- append and scan

### `record_log_append_no_fsync`

| Payload | Mean time | Throughput |
| ------- | --------- | ---------- |
| 64 B    | ~780 ns   | ~78 MiB/s  |
| 1 KiB   | ~1.19 µs  | ~822 MiB/s |
| 64 KiB  | ~24.8 µs  | ~2.47 GiB/s |

Small payloads expose framing and write-syscall overhead; large
payloads approach the memory/page-cache bandwidth ceiling.

### `record_log_append_fsync_each`

| Payload | Mean time | Throughput |
| ------- | --------- | ---------- |
| 64 B    | ~3.72 µs  | ~16 MiB/s   |
| 1 KiB   | ~4.38 µs  | ~223 MiB/s  |
| 64 KiB  | ~27.5 µs  | ~2.22 GiB/s |

The delta against `append_no_fsync` (~3 µs) is the per-fsync cost on
this stack. **This number is highly filesystem- and
storage-dependent.** See [`../benchmarks.md`](../benchmarks.md)
*fsync gotchas* for the failure modes that make this number a lie.

### `record_log_scan`

| Records | Mean time | Throughput      |
| ------- | --------- | --------------- |
| 1 000   | ~122 µs   | ~8.2 Melem/s    |
| 10 000  | ~1.18 ms  | ~8.5 Melem/s    |

Scan rate is roughly constant across the tested range, which means
the cache locality of the segment reader is reasonable for these
sizes.

## `datawal_kv` -- put / get / delete / open

### `datawal_put`

| Keydir size | Mean time |
| ----------- | --------- |
| 1 000       | ~942 ns   |
| 10 000      | ~893 ns   |
| 100 000     | ~1.03 µs  |

Approximately constant: put cost does not depend on keydir size.

### `datawal_get`

| Keydir size | Mean time |
| ----------- | --------- |
| 1 000       | ~29.9 ns  |
| 10 000      | ~38.8 ns  |
| 100 000     | ~46.3 ns  |

Mild growth with keydir size reflects HashMap cache-pressure effects;
nothing unexpected.

### `datawal_delete`

| Keydir size | Mean time |
| ----------- | --------- |
| 1 000       | ~1.64 µs  |
| 10 000      | ~1.65 µs  |
| 100 000     | ~1.70 µs  |

Delete is ~70 % slower than put on this stack, consistently across
keydir sizes. Tracked as a future investigation question; current code
path is sound but may have an extra `contains_key` call before the
tombstone append.

### `datawal_open_rebuild`

| Records replayed | Mean time |
| ---------------- | --------- |
| 1 000            | ~311 µs   |
| 10 000           | ~2.95 ms  |
| 100 000          | ~39.0 ms  |

Roughly linear: ~400 ns/record amortised. Cold-open of a 1 M-record
log would extrapolate to ~400 ms on this stack.

## `compaction` -- `compact_to` and `export_jsonl`

### `compact_to`, delete-heavy

| Live ratio | Mean time |
| ---------- | --------- |
| 100 %      | ~8.36 ms  |
| 50 %       | ~4.11 ms  |
| 10 %       | ~861 µs   |

Scales linearly with live key count. `compact_to` cost is dominated
by writing the live keys, not by reading the source log.

### `compact_to`, overwrite-heavy

| Live ratio | Mean time |
| ---------- | --------- |
| 100 %      | ~8.44 ms  |
| 50 %       | ~8.37 ms  |
| 10 %       | ~8.42 ms  |

Approximately constant across live ratios because the keydir size is
constant (overwrites do not shrink the keydir; only deletes do).
Confirms that `compact_to` iterates the keydir, not the source log.

### `export_jsonl`

| Live ratio | Mean time |
| ---------- | --------- |
| 100 %      | ~2.65 ms  |
| 50 %       | ~1.27 ms  |
| 10 %       | ~249 µs   |

About 3× faster than `compact_to` at the same live ratio, because
JSONL is a single-file write rather than a framed log rebuild.

## `recovery` -- open scenarios

### `recovery_open_clean`

| Records | Mean time |
| ------- | --------- |
| 1 000   | ~122 µs   |
| 10 000  | ~951 µs   |

Roughly linear in record count, slightly sub-linear from amortised
fixed overhead.

### `recovery_open_multi_segment`

| Segments (500 records each) | Mean time |
| --------------------------- | --------- |
| 1                           | ~73 µs    |
| 4                           | ~215 µs   |
| 16                          | ~786 µs   |

Sub-linear in segment count; each additional segment adds ~45-50 µs
of fixed overhead.

### `recovery_open_with_tail_truncation`

| Bytes truncated from last segment | Mean time |
| --------------------------------- | --------- |
| 1                                 | ~115 µs   |
| 64                                | ~115 µs   |
| 1024                              | ~115 µs   |

Independent of truncation size, as expected. Recovery cost is the
scan up to the last valid record; the size of the trailing garbage is
irrelevant.

## How to make this comparable on your machine

```sh
# 1. Quiet the machine: close browsers, pause background jobs.
# 2. Point at a real local disk for honest fsync numbers.
export DATAWAL_BENCH_DIR=/path/to/real/disk/bench

# 3. Save a baseline before any change.
just bench-baseline ref

# 4. Run your variant and compare.
# ... change code ...
just bench-compare ref
```

If you see structural differences (e.g. `compact_to overwrite-heavy`
no longer constant across live ratios, `put` growing with keydir size,
`tail_truncation` growing with truncation size), that is interesting
and probably worth investigating. Constant-factor differences are
expected and uninteresting.
