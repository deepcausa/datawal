# v0.1.4 reference bench run

A single reference run, frozen at the v0.1.4 tag. **This is not a
specification. It is not a target. It is not a guarantee.** Your
numbers will differ -- often substantially -- depending on filesystem,
storage class, CPU, kernel, and what else is running on the box.

The point of this document is to give you something to compare against
if your local numbers look wildly off (10× worse: probably bug or slow
disk; 10× better: implausible, check your fsync semantics).

For methodology, what each bench measures, and how to read Criterion
output, see [`../benchmarks.md`](../benchmarks.md).

| | |
| --- | --- |

| `DATAWAL_BENCH_DIR` | set to a directory on the ext4 mount above |

Raw-fsync sanity check on the same mount before the run:

```text
fsync(64B file) on ext4: median 1785 us, p10 1720 us, p90 1858 us
fsync(64B file) on tmpfs (/tmp): median 0.59 us, p10 0.57 us, p90 0.63 us
```

The `append_fsync_each` numbers below are dominated by that ~1.78 ms
per-fsync floor; the no-fsync and scan numbers are unaffected.

## What changed since `v0.1.0-alpha`

`v0.1.4` consolidates the 8-PR quality kit described in
[`../../CHANGELOG.md`](../../CHANGELOG.md). The two structural changes
that should move benchmark numbers:

1. **Keydir stores `RecordRef` (offset), not `Vec<u8>` (value).** This
   trades memory pressure for an extra `pread + CRC32C verify` on
   every `DataWal::get` and inside `compact_to` / `export_jsonl`.
   - `datawal_put`: unchanged (still one frame append + one HashMap
     write).
   - `datawal_get`: pays the cost of one `pread` + one CRC32C verify
     per call. On a warm page cache this stays in the low-µs range.
   - `datawal_open_rebuild`: recovery does not materialise values
     into the keydir, only `RecordRef`s.
   - `compact_to` and `export_jsonl`: I/O-sensitive, because they
     re-read each live value from disk via the fd pool rather than
     copying values held in memory.
   - Memory footprint per live key: drops from roughly
     `key_len + value_len + overhead` to roughly
     `key_len + 32 bytes + overhead`.
2. **`RecordLogReader` (lockless concurrent reader).** Not exercised
   by the existing benches but introduces no overhead on the writer
   path. Read-side throughput is bounded by `RecordLog::scan_iter`
   numbers below.

The frame layout (`MAGIC + 24-byte header + key + payload + 4-byte
CRC32C`) is identical to `v0.1.0-alpha`. Recovery semantics are
unchanged.

## `record_log` -- append and scan

### `record_log_append_no_fsync`

| Payload | Mean time | Throughput |
| ------- | --------- | ---------- |
| 64 B    | ~857 ns   | ~71 MiB/s   |
| 1 KiB   | ~1.44 µs  | ~679 MiB/s  |
| 64 KiB  | ~34.7 µs  | ~1.76 GiB/s |

Small payloads expose framing and write-syscall overhead; large
payloads approach the memory/page-cache bandwidth ceiling.

### `record_log_append_fsync_each`

| Payload | Mean time | Throughput  |
| ------- | --------- | ----------- |
| 64 B    | ~1.78 ms  | ~35 KiB/s   |
| 1 KiB   | ~1.72 ms  | ~583 KiB/s  |
| 64 KiB  | ~1.85 ms  | ~33.7 MiB/s |

The numbers are dominated by the ~1.78 ms per-fsync floor on this
ext4 stack (see [Stack](#stack) for the raw-fsync sanity check). The
delta against `append_no_fsync` is essentially the cost of one
`sync_all` plus one directory fsync per record. **This number is
highly filesystem- and storage-dependent.** See
[`../benchmarks.md`](../benchmarks.md) *fsync gotchas* for the
failure modes that make this number a lie if measured carelessly
(notably tmpfs, where the same bench would report sub-microsecond
fsync because the syscall is a no-op).

### `record_log_append`

| Payload | Mean time | Throughput  |
| ------- | --------- | ----------- |
| 64 B    | ~733 ns   | ~83 MiB/s   |
| 1 KiB   | ~1.15 µs  | ~850 MiB/s  |
| 64 KiB  | ~24.4 µs  | ~2.50 GiB/s |

Parity bench (no fsync) added in the kit. Numbers are slightly faster
than `record_log_append_no_fsync` because of a tighter inner loop;
both measure the same conceptual cost.

### `record_log_scan`

| Records | Mean time | Throughput   |
| ------- | --------- | ------------ |
| 1 000   | ~120 µs   | ~8.3 Melem/s |
| 10 000  | ~1.14 ms  | ~8.8 Melem/s |

Scan rate is roughly constant across the tested range; the
segment-buffered reader handles both sizes uniformly.

### `record_log_scan_iter_collect`

| Records | Mean time | Throughput    |
| ------- | --------- | ------------- |
| 1 000   | ~100 µs   | ~10.0 Melem/s |
| 10 000  | ~937 µs   | ~10.7 Melem/s |

`scan_iter` (record-level lazy iterator, segment-buffered, not
zero-copy) added in the kit. Slightly faster than the eager `scan()`
on this stack because it skips materialising the full `Vec<Record>`.

### `record_log_scan_iter_early_stop`

| Records to consume | Mean time |
| ------------------ | --------- |
| 1 000              | ~18.9 µs  |
| 10 000             | ~108 µs   |

Early-stop bench: consume `N` records via `scan_iter` then drop it.
Demonstrates the iterator does not eagerly read past what the caller
consumes — about 1 µs per consumed record, plus open overhead.

## `datawal_kv` -- put / get / delete / open

### `datawal_put`

| Keydir size | Mean time |
| ----------- | --------- |
| 1 000       | ~975 ns   |
| 10 000      | ~987 ns   |
| 100 000     | ~1.12 µs  |

Approximately constant: put cost does not depend on keydir size.

### `datawal_get`

| Keydir size | Mean time |
| ----------- | --------- |
| 1 000       | ~686 ns   |
| 10 000      | ~711 ns   |
| 100 000     | ~780 ns   |

Mild growth with keydir size from HashMap cache pressure. Includes
the per-call `pread` + CRC32C verify introduced in PR #28
(keydir-by-offset). On a warm page cache this stays in the
sub-microsecond range. The trade-off — losing the previous nanosecond-scale
in-memory hits in exchange for `O(keys)` memory instead of
`O(keys + values)` — is documented in
[the kit summary](#what-changed-since-v010-alpha).

### `datawal_delete`

| Keydir size | Mean time |
| ----------- | --------- |
| 1 000       | ~1.79 µs  |
| 10 000      | ~1.84 µs  |
| 100 000     | ~1.88 µs  |

Delete remains slightly slower than put, consistently across keydir
sizes.

### `datawal_open_rebuild`

| Records replayed | Mean time |
| ---------------- | --------- |
| 1 000            | ~2.02 ms  |
| 10 000           | ~4.04 ms  |
| 100 000          | ~25.6 ms  |

Roughly linear in record count. The offset-keydir does not
materialise values during recovery — it only records the `RecordRef`
for each live key — which keeps replay cheap even on logs with
multi-KB payloads.

## `compaction` -- `compact_to` and `export_jsonl`

### `compact_to`, delete-heavy

| Live ratio | Mean time |
| ---------- | --------- |
| 10 %       | ~7.72 ms  |
| 50 %       | ~15.7 ms  |
| 100 %      | ~27.1 ms  |

Roughly linear in live key count. Two factors set the absolute cost
on this stack:
1. The fsync floor (~1.78 ms; see [Stack](#stack) raw-fsync sanity
   check). Every `compact_to` finishes with one `sync_all` + one
   directory fsync.
2. PR #28: `compact_to` re-reads each live value from disk via the
   fd-pool LRU and re-verifies CRC, rather than copying values
   already in memory. Trade-off: same memory benefit as `datawal_get`,
   same I/O cost.

### `compact_to`, overwrite-heavy

| Live ratio | Mean time |
| ---------- | --------- |
| 10 %       | ~26.2 ms  |
| 50 %       | ~26.4 ms  |
| 100 %      | ~26.2 ms  |

Approximately constant across live ratios, as expected: overwrites do
not shrink the keydir (only deletes do), so `compact_to` always
iterates the same number of live keys.

### `export_jsonl`

| Live ratio | Mean time |
| ---------- | --------- |
| 10 %       | ~5.01 ms  |
| 50 %       | ~10.4 ms  |
| 100 %      | ~17.3 ms  |

About 1.5–2× faster than `compact_to delete-heavy` at the same live
ratio: JSONL is a single-file `write + fsync` rather than a framed
log rebuild with directory fsync.

## `recovery` -- open scenarios

### `recovery_open_clean`

| Records | Mean time |
| ------- | --------- |
| 1 000   | ~1.92 ms  |
| 10 000  | ~4.77 ms  |

Roughly linear in record count. Includes the cooperative
single-writer lock acquisition + the `RecordLog` scan + the
offset-keydir build + one fsync of the lock directory and the active
segment metadata. On a stack with no-op fsync (tmpfs) the absolute
numbers would be one to two orders of magnitude lower; the
per-fsync floor (~1.78 ms here) is the dominant term at small record
counts.

### `recovery_open_multi_segment`

| Segments (500 records each) | Mean time |
| --------------------------- | --------- |
| 1                           | ~1.83 ms  |
| 4                           | ~2.04 ms  |
| 16                          | ~2.78 ms  |

Sub-linear in segment count; each additional segment adds ~50–60 µs
of fixed overhead (open + size check + final record offset compute).

### `recovery_open_with_tail_truncation`

| Bytes truncated from last segment | Mean time |
| --------------------------------- | --------- |
| 1                                 | ~1.92 ms  |
| 64                                | ~1.91 ms  |
| 1024                              | ~1.93 ms  |

Independent of truncation size, as expected. Recovery cost is the
scan up to the last valid record; the size of the trailing garbage
is irrelevant.

## How to make this comparable on your machine

```sh
# 1. Quiet the machine: close browsers, pause background jobs.
# 2. Point at a real local disk for honest fsync numbers.
#    On Linux, /tmp is often tmpfs — fsync there is a no-op and
#    numbers will be misleadingly fast.
export DATAWAL_BENCH_DIR=/path/to/real/disk/bench
findmnt -no FSTYPE --target "$DATAWAL_BENCH_DIR"   # must NOT be tmpfs/overlay

# 3. Save a baseline before any change.
just bench-baseline ref

# 4. Run your variant and compare.
# ... change code ...
just bench-compare ref
```

If you see structural differences (e.g. `compact_to overwrite-heavy`
no longer constant across live ratios, `put` growing with keydir size,
`tail_truncation` growing with truncation size), that is interesting
and probably worth investigating. Constant-factor differences are
expected and uninteresting.
