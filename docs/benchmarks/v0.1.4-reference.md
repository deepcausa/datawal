# v0.1.4 reference bench run

A single reference run, frozen at the v0.1.4 tag. **This is not a
specification. It is not a target. It is not a guarantee.** Your
numbers will differ -- often substantially -- depending on filesystem,
storage class, CPU, kernel, and what else is running on the box.

The point of this document is to give you something to compare against
if your local numbers look wildly off (10× worse: probably bug or slow
disk; 10× better: implausible, check your fsync semantics).

For methodology, what each bench measures, and how to read Criterion
output, see [`../benchmarks.md`](../benchmarks.md). For the historical
reference numbers, see
[`v0.1.0-alpha-reference.md`](v0.1.0-alpha-reference.md).

A note on the storage class: NVMe drives with PLP can legitimately
acknowledge `fsync` in single-digit microseconds because the controller
considers writes durable once they reach the supercapacitor-backed
write cache. The observed fsync latencies below reflect that. On
consumer SSDs without PLP, expect fsync latencies one to two orders of
magnitude higher.

## What changed since `v0.1.0-alpha`

`v0.1.4` consolidates the 8-PR quality kit described in
[`../../CHANGELOG.md`](../../CHANGELOG.md). The two structural changes
likely to move benchmark numbers:

1. **Keydir stores `RecordRef` (offset), not `Vec<u8>` (value).** This
   trades memory pressure for an extra `pread + CRC32C` on every
   `DataWal::get`. Expect:
   - `datawal_put`: unchanged (still one frame append + one HashMap
     write).
   - `datawal_get`: slower than the alpha reference, by the cost of
     one `pread` + one CRC32C verify per call. On a warm page cache
     this should remain in the low-µs range.
   - `datawal_open_rebuild`: faster than the alpha reference, since
     the recovery no longer materialises every value into the keydir.
   - Memory footprint per live key: drops from
     `key_len + value_len + overhead` to roughly
     `key_len + 32 bytes + overhead`.
2. **`RecordLogReader` (lockless concurrent reader).** Not exercised
   by the existing benches but introduces no overhead on the writer
   path. Read-side throughput is bounded by `RecordLog::scan_iter`
   numbers below.

The frame layout (`MAGIC + 24-byte header + key + payload + 4-byte
CRC32C`) is identical to `v0.1.0-alpha`. Recovery semantics are
unchanged.

## How to make this comparable on your machine

```sh
# 1. Quiet the machine: close browsers, pause background jobs.
# 2. Point at a real local disk for honest fsync numbers.
export DATAWAL_BENCH_DIR=/path/to/real/disk/bench

# 3. Save a baseline before any change.
just bench-baseline ref

# 4. Run your variant and compare.
# ... change code ...
just bench-compare ref
```

If you see structural differences (e.g. `compact_to overwrite-heavy`
no longer constant across live ratios, `put` growing with keydir size,
`tail_truncation` growing with truncation size), that is interesting
and probably worth investigating. Constant-factor differences are
expected and uninteresting.
